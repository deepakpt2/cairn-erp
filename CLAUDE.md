## Token & Context Optimization Rules
These are standing rules for every session. Follow them even when a task seems to need an exception; ask the user instead.

1. **Migration history isolation.** Never read, grep or search `./drizzle/history/` (386 superseded migrations, 2.4 MB).
   - Always exclude it from searches: `grep -r --exclude-dir=history …`, `rg --glob '!drizzle/history/**' …`, `find … -path ./drizzle/history -prune -o …`. Never `cat`/`head`/`sed` a file under it.
   - `.claude/settings.json` denies `Read(./drizzle/history/**)` for the file tools; that rule does not cover shell commands, so the exclusions above are required.
   - Current schema lives in `src/**/schema*.ts`, `src/platform/tables/*.ts`, `drizzle/0000_baseline.sql` and `drizzle/9*.sql`. To check a historical migration use `git log -S '<name>' -- drizzle/`, or ask the user.
   - Never delete or move the folder, or add it to `.gitignore`: schema-contract tests and `scripts/lint-ip.ts` read it.
2. **Import graph querying.** Never read `docs/codemap/import-graph.json` (280 KB) whole into context: not with Read, `cat`, `head` or a large line range. Always query it with `jq`; keys are paths relative to `src/`.
   - Imports of a file: `jq '."modules/quality/lot.ts"' docs/codemap/import-graph.json`
   - Importers of a file: `jq -r 'to_entries[] | select(.value | index("platform/db/client.ts")) | .key' docs/codemap/import-graph.json`
3. **Codemap usage.** Treat `docs/codemap/*` as index tables (`file | exports | tables`), not documents. Never load a whole codemap file into context; read only the row or block you need.
   - One row: `grep -n '<file or table>' docs/codemap/modules/<m>.md` or `grep -rn '<name>' docs/codemap/*.md docs/codemap/modules/`
   - Gotchas only (read before changing a module): `awk '/^## Gotchas/{p=1;next} /^## /{p=0} p' docs/codemap/modules/<m>.md`

## Business logic placement
Business logic must be built as **service functions in `src/modules/<module>/*.ts`**, not inline in `src/app/*`. This is the existing pattern across every module — follow it for all new work:
- `src/modules/<module>/<feature>.ts` — the real logic: validation, DB reads/writes (via `withTenant`/`Tx`), posting, capability constants, typed errors (`class XError extends Error`). This is what gets imported and reused (by other modules, tests, scripts).
- `src/app/<module>/<feature>/actions.ts` — a thin `'use server'` wrapper: parses `FormData`/args, calls the service function, maps its typed error to UI state (`{ ok, message, remedy }`), calls `revalidatePath`. No business logic here — it's just presentation glue around the service call.
- `src/app/<module>/<feature>/page.tsx` / `*.tsx` — reads via the service function, renders, delegates writes to `actions.ts`.

Keep this split even for small features. When a new module/feature doc is needed, reflect it in `docs/codemap/modules/<module>.md`.

## Printable payslip (people / payroll)

`/people/payroll-results` links **Print / Save as PDF** to the protected route handler `/people/payroll-results/payslip?result=…` (`src/app/people/payroll-results/payslip/route.ts`). The service is `getPayslip` in `src/modules/people/payroll-payslip.ts`; it is a read-only view of the stored result and its lines — never a recalculation, posting or payment.

- **Final results only.** RELEASED and POSTED print; PROPOSED (`PAYSLIP_NOT_FINAL`) and CANCELLED (`PAYSLIP_CANCELLED`) are refused server-side.
- **Authority is re-judged in the service tx:** the live session, `PEOPLE.PAYROLL.RESULT`/`PEOPLE.PAYROLLRUN.EXECUTE`, and the run's Company Code reach. Tenant and user come from the session; `?result=` only names a result the caller already reaches. An unreachable result answers like a missing one (`PAYSLIP_UNAVAILABLE`, 404) — do not add a different response, it would become a probe.
- **Persisted amounts only.** Gross/deductions/net are `payroll_result` columns written at `currency.decimal_places` (never a fixed 2). Employer contributions are a separate section and never enter deductions or net. There is no recalculation and no summing of subtotals.
- **No sensitive internals.** G/L accounts, cost receivers and bank details are excluded. The page has no script, image, font or external resource; the route is `private, no-store` with a `default-src 'none'` CSP. It is not cached and not linked publicly.
- **Not a payment.** The page says the payslip is a payroll calculation, not evidence a bank payment succeeded, and makes no statutory-compliance claim.
- **No new screen or PDF library.** Browser Print → Save as PDF is the supported workflow. `pdf-lib` is not used for payslips, and bulk generation / email / employee self-service are out of scope.

## Generic salary payment file (people / payroll)

`/people/payroll-runs` has a **Generic salary payment file** panel on a POSTED run. It prepares and downloads a **generic CSV working file** the user converts and uploads to their bank manually. It is **not a bank format**, the ERP never sends it, and no bank/country is asserted to accept it. Service: `src/modules/people/payroll-payment-file.ts` (migration `9320`, table `payroll_payment_file`); route: `src/app/people/payroll-runs/payment-file/route.ts` (`POST` prepare, `GET` download).

- **POSTED only, frozen results.** One row per positive net pay, exact at `currency.decimal_places` (no floating point). Zero net dropped; negative net, no payable rows and a count/total mismatch against a salary payment refuse the file.
- **One batch per run.** Unique `(client, run_id)`; `POST` is idempotent under a run advisory lock (a concurrent/retry call returns the same snapshot). A different intended date on an existing batch is refused (`FILE_EXISTS`), never rewritten. The CSV body is stored byte-identically, so a re-download ignores later master-data changes.
- **Blank bank columns.** No authorised employee bank master exists, so `beneficiary_bank_name/bank_code/account/iban` are exported empty; the user completes them in the bank's file. No employee is dropped for missing details.
- **Authority, fail closed.** Preparing/downloading the file requires BOTH `PEOPLE.PAYROLL.FILE.EXPORT` (9320) AND `PEOPLE.BANK.REVEAL` — the CSV embeds each employee's full IBAN/account number, so export alone is refused (`FILE_BANK_AUTHORITY`). Both granted to no role; the live session, the run's Company Code and **every** included employee's reach are judged in the service transaction. An unreachable run answers like a missing one (`FILE_UNAVAILABLE`, 404); never return a partial file.
- **Duplicate-upload guard.** Every download after the first needs `confirm=yes` (`FILE_REUSE`, 409): a second external upload can pay twice and the ERP cannot see the bank. It is not a reissue workflow — a wrong date/data is resolved by an administrator.
- **Reversal is terminal here.** A reversed payroll posting or salary payment refuses prepare and download (`RUN_REVERSED`/`PAYMENT_REVERSED`); nothing is auto-reissued.
- **Separation of concerns.** Preparing/downloading posts nothing, clears nothing and marks no salary paid. The `PY` salary payment is accounting only — not proof a transfer reached an employee. Bank acceptance, settlement and reconciliation are external/manual.
- **Privacy.** `private, no-store`; audit logs who/when/file reference/run/count/total only — never the CSV, account fields or salary line items. CSV cells are RFC 4180 quoted and formula-like leads (`= + - @`) are prefixed with an apostrophe.

## Employee salary bank details (people, infotype 0009)

`/people/employees` (open an employee) has a **Salary bank details** section, and the generic payment CSV carries it. Service: `src/modules/people/employee-bank.ts` (migration `9321`, table `employee_bank_detail`); actions: `src/app/people/employees/bank-actions.ts`; UI: `EmployeeBank.tsx`.

- **Effective-dated, one main account at a time.** A gist exclusion constraint forbids two active main rows whose inclusive dates overlap — atomic, including concurrent writers (a per-employee advisory lock is the pre-check). A change is a new record: end the current one, add a new one; history is never overwritten. Future-dated changes are allowed.
- **Encrypted only.** The account number/IBAN is stored as an AES-256-GCM envelope (`cbd1…`) from the bank-data keyring, authenticated to tenant + employee + record id + field. No plaintext column, change-log value, audit value, log line or URL. An unavailable keyring fails closed.
- **Three least-privilege capabilities, granted to no role:** `PEOPLE.BANK.VIEW` (masked, `••••1234`), `PEOPLE.BANK.MAINTAIN` (add/end), `PEOPLE.BANK.REVEAL` (full value, audited). Every call re-judges the live session, capability and employee company/plant reach via `ServiceAuthorityContext`; bank records answer like unknown ones out of reach.
- **Reveal audit:** actor, action, employee/record reference, purpose and timestamp — never the account number.
- **Not a bank format.** The records only populate the generic CSV; the conversion/upload warning still applies, and reveal/creation does not post or pay.

### Wiring into the CSV (`payroll-payment-file.ts`, migration `9322`)

- At preparation, the effective main account is selected **as of the intended payment date** (`accountAsOf`), not today. Missing or ambiguous details refuse with an employee-level list — no partial file, no guess.
- The frozen rows and the account identifier are snapshotted in `payroll_payment_file.bank_snapshot`: clear metadata + the identifier as an AES-256-GCM envelope bound to tenant + employee + **file id**. `body` is NULL for such a file; the CSV is rebuilt deterministically from the snapshot at download, and an unavailable keyring fails the download closed. A re-download after later master-data changes reproduces the same file.
- A **legacy** file (pre-9322: plaintext `body`, `bank_data_included = false`, empty snapshot) downloads byte-for-byte and is never silently changed or regenerated — resolving it is a controlled process, not this screen.

## Private salary-file storage (people / payroll, migration 9325)

Generated payment CSVs (original files and approved replacements) are retained on **private host storage**, not in the database:
- `src/platform/security/artifact-encryption.ts` — AES-256-GCM `cad1.` envelope reusing the deployment `CAIRN_BANK_DATA_KEYRING_JSON`, AAD-bound to tenant + artifact id + field, size-capped (32 MB) for CSVs.
- `src/platform/security/artifact-store.ts` — `CAIRN_PAYMENT_FILE_DIR` private dir; paths `<tenant>/<uuid>.enc` only (no client fragments, traversal rejected); 0700/0600 where possible; temp-file + fsync + atomic rename; refuses overwrite.
- `src/modules/people/payment-file-artifacts.ts` — `retainArtifact` (encrypt → write durably → insert `payroll_payment_artifact` metadata, all inside the owner's transaction) and `readArtifact` (verifies plaintext SHA-256; returns null on any failure). Metadata carries owner (FILE+preparation_id / REISSUE+reissue_id), storage path, key id, sha256, length, `changed_by`/`changed_at` — never plaintext or a URL.
- Preparation retains the FILE artifact; approval retains the REISSUE artifact — both before the row advertises success, so a committed row always has a file. Downloads prefer the retained bytes (byte-identical across restarts and later bank changes); a **missing/unreadable artifact fails closed** (`FILE_ARTIFACT_UNAVAILABLE`/`REISSUE_ARTIFACT_UNAVAILABLE`), never rebuilt as a substitute. Legacy rows (no artifact) rebuild deterministically from the immutable snapshot or return the stored body.
- **Crash safety.** A publish writes to a private staging temp (every byte checked, short writes retried), fsyncs the file, atomically renames to `<tenant>/<uuid>.enc`, then **fsyncs the tenant directory** so the name survives power loss. The metadata row commits after; a failed commit can leave an encrypted orphan, never a partial published file.
- **Marker, not "absent = legacy".** `payroll_payment_artifact_state` (migration 9326) marks a NEW-format owner (written in the same transaction). A new-format owner whose artifact is missing **fails closed** (`FILE_ARTIFACT_UNAVAILABLE`/`REISSUE_ARTIFACT_UNAVAILABLE`); only a genuinely legacy owner (no marker) may rebuild from its stored body/immutable snapshot.
- **Sweeper isolation contract.** `sweepOrphans` refuses any transaction that is not READ COMMITTED (`ARTIFACT_ISOLATION`): after waiting for the exclusive lock its reference SELECT must be a fresh statement, which a REPEATABLE READ snapshot is not. Directory parent entries are flushed on EVERY publication (not only when this call created the directory), because writers share the lock and cannot assume another writer flushed it.
- **Publisher/sweeper serialisation (safety, not a timeout).** Every publisher (original preparation, replacement approval, backfill) takes a tenant-scoped PostgreSQL transaction-level **shared** advisory lock (`payment-artifact:<client>`) BEFORE writing staging/published storage and holds it until commit/rollback. The sweeper takes the same tenant lock **exclusive** as its first statement, so it waits for every in-flight publisher; its reference read is then a fresh READ COMMITTED statement that sees their commits. A grace period remains only as an extra condition for crashed-transaction leftovers. Lock order: employee-bank → reissue-state → artifact (publishers); sweeper takes only the artifact lock.
- **Reconciliation/backfill.** `sweepOrphans` removes `.enc` files with no committed metadata row (only after a grace period, so an in-flight publish is never touched) and stale staging temps; it never deletes a referenced artifact. `backfillLegacyArtifact` retains EXACT legacy bytes only when they match the stored checksum; otherwise `unverifiable`, nothing written. Operator CLI: `npm run payment-file:maintenance` (`CAIRN_ARTIFACT_COMMAND=sweep|backfill`).
- **Deployment.** The shipped Compose file uses a named volume `payment_files` (mounted at `/app/payment-files`, outside the checkout/web root); the app image creates that directory owned by UID/GID 1001. A host bind mount must be initialised to UID/GID 1001 (mode 700, never world-readable); the app does not assume the deployer's UID. `.dockerignore` excludes any repository-local `payment-files/`. Back up the volume with the keyring; losing either is unrecoverable. See `docs/fresh-server-installation.md` §3b.
- **Durable submission intent (9328), register → execute.** The screen REGISTERS the exact normalized request (row in `payroll_payment_reissue_intent`, status `REGISTERED`, keyed by the stable `request_key`, holding the payload server-side) and only then EXECUTES it. Registration never creates a draft. Phase 1 commits `RUNNING` before the draft is attempted; phase 2 commits the draft and `COMPLETED` (with `reissue_id`) in one transaction. A truly final content refusal sets `REFUSED`; an environmental conflict leaves `RUNNING` and stays retryable. `executeReissueIntent` replays a `COMPLETED` intent BEFORE new-request eligibility checks, so an existing active draft cannot block recovery. Recovery survives lost responses, tab close, reload, and disabled/cleared browser storage; a failed recovery check blocks dispatch. The recovery list is requester-scoped, payload-free, and rechecks tenant/company/employee reach. No payload, employee number, reason or evidence reference is ever written to browser storage; a legacy v2 marker is scrubbed to its opaque key only and reconciled server-side (no payload replay).
- **Ambiguous outcomes are never "nothing was saved".** A mutating POST treats only a 4xx application refusal as definite; transport errors, unreadable 2xx bodies, 5xx and 408 are UNKNOWN. The same unresolved logical request keeps its key AND exact payload, restored per-source (sessionStorage, keyed by preparation id, per tab) so a reload retry reuses them; the server `reconcile` action reports a draft only to its own requester and source under the request-key lock — a "not found" is not proof a delayed attempt cannot commit, so the warning stays until a draft is found or the user explicitly abandons.
- **Review assertion is enforced in the SERVICE**, not only the route: `approveReissue` requires `reviewedAssertion: true` **and** a matching full-review digest, validated in the approval transaction under the bank+state locks; the assertion + digest are recorded in the sanitized audit. Reach for the original run's company and every included employee is checked before any status/reference is returned (approval, cancel, ordinary/historical download).

## Controlled salary-file reissue (people / payroll, migration 9323)

`PaymentReissuePanel` on `/people/payroll-runs` (when a prepared file exists) drives the replacement workflow; service `src/modules/people/payroll-payment-reissue.ts`; route `src/app/people/payroll-runs/payment-file/reissue/route.ts` (`POST` preview/request/approve/cancel, `GET` download/historical). Tables `payroll_payment_reissue` + `payroll_payment_reissue_line`.

- **Attestation, not bank truth.** Each selected employee needs a user-attested original outcome (`NOT_UPLOADED`, `BANK_REJECTED`, `CANCELLED_BEFORE_EXECUTION`, `RETURNED`) + reason + verification date + evidence reference; `NOT_UPLOADED` also needs `confirmedNoSubmission`. Unknown/pending/paid/“cancellation requested” is refused. The ERP cannot revoke an uploaded file.
- **All-or-selected, frozen amounts only.** `selection` is `ALL` or `SELECTED`; every selected employee must be in the source file. The replacement reuses each employee's **original frozen net amount/currency** from the source snapshot (never recalculated, never editable) and re-selects bank details **as of the replacement intended date** (`accountAsOf`). Missing/ambiguous/out-of-reach refuse the whole request (no partial file).
- **Four eyes.** `requestReissue` creates a DRAFT (capability `PEOPLE.PAYROLL.REISSUE.REQUEST`); a **different** approver (`…APPROVE`) releases it. Approval re-checks the exact frozen snapshot (canonical JSON checksum), re-checks every employee's eligibility/reach and refuses if a newer approved attempt for the same employee appeared after the draft was requested (`REISSUE_STALE`).
- **Legacy files** (plaintext `body`, no snapshot) are parsed back into rows so they remain eligible for replacement; their stored bytes are never changed.
- **Scope on every call.** list/cancel/download re-check the run's Company Code and every included employee's reach (`REISSUE_UNAVAILABLE` otherwise); `downloadReissue` also refuses a reversed posting/payment and computes `reused` from PRIOR downloads only.
- **One draft per obligation.** Partial unique index `(client, run_id, personnel_number) where state = 'DRAFT'` + a per-run advisory lock: concurrent/retried requests can't form two drafts; a same `requestKey` replays; a standing draft is `REISSUE_CONFLICT`.
- **Immutable, encrypted snapshot.** Account identifiers are stored as AES-256-GCM envelopes bound to tenant+employee+reissue id (never plaintext, log, audit or URL). Download rebuilds the CSV from the frozen snapshot (`paymentRowsFromSnapshot`); keyring unavailable fails closed. Re-download is byte-identical (`private, no-store`).
- **Historical replacement evidence.** `downloadHistoricalReissue` serves a superseded replacement as protected evidence — rebuilt from the immutable snapshot with the same integrity/keyring checks, byte-identical to the earlier ordinary download, filename `HISTORICAL-DO-NOT-UPLOAD-…`, marked do-not-upload, requiring `FILE_HISTORICAL` + live `PEOPLE.BANK.REVEAL`. The view computes `superseded`/`downloadable` per replacement (any line superseded → whole file historical), so the screen offers an ordinary Download only while it is current and a Historical action otherwise; the server rechecks.
- **Every old generation blocked.** A replacement download checks each employee against the LATEST approved attempt; if any line is superseded (a later approved replacement exists for that employee) the whole old file is refused (`REISSUE_SUPERSEDED`). The same holds for the source file (`FILE_SUPERSEDED`). Superseded snapshots stay readable only as `downloadHistoricalFile` (`…FILE.HISTORICAL`, marked `HISTORICAL … do not upload`, never regenerated). Download holds the same per-run lock as approval so a racing approval cannot slip past the guard.
- **Full identifiers need bank authority.** `downloadReissue` and `downloadHistoricalFile` require their own capability AND live `PEOPLE.BANK.REVEAL` (`REISSUE_BANK_AUTHORITY` otherwise) — matching the original file. Masked previews/reviews never decrypt beyond a mask.
- **Scope on every read.** `listReissues`, `listReissueSourceEmployees` and whole-file `previewReissue` fail closed (`FILE_UNAVAILABLE`/`REISSUE_UNAVAILABLE`) if any included employee is outside the caller's live reach; selected previews prove each named employee is reachable before returning anything; an idempotent replay re-checks scope before returning. Out-of-scope and missing are indistinguishable.
- **Approver review + deliberate confirmation.** The screen shows the frozen employees, frozen beneficiary, amounts, masked bank, intended date, predecessor, reason and each attestation, and requires an acknowledgement bound to the snapshot: the approval POST carries `confirmDigest` = a review digest over the header and EVERY line (destination, amount, predecessor, reason, attestation/evidence) **and** `confirmReviewed=yes`; the service itself requires `reviewedAssertion: true`. The service requires it (`REISSUE_CONFIRMATION_REQUIRED`/`_STALE`) and records it in the audit. Four-eyes stays server-enforced; changing source/selection/date invalidates the preview (generation token discards stale in-flight responses).
- **Full destination check, fail closed.** Approval compares the WHOLE payment destination (frozen beneficiary, bank name/code, account kind, decoded account) against the effective main account on the intended date. A changed beneficiary/bank/kind with the same number, or unreadable data (`REISSUE_BANK_UNREADABLE`), refuses (`REISSUE_BANK_CHANGED`) — never "unchanged by omission". Bank maintenance and approval share the per-employee `employee-bank:` lock (see `payment-file-locks.ts` for lock ordering: bank locks sorted, then `payment-reissue-state:`; a `payment-reissue-key:` lock serialises request-key reuse). The original file's ordinary download also takes the state lock, so supersession and approval are serialised.
- **Idempotency fingerprint.** A request key replays only an identical normalized request — a canonical `request_fingerprint` (migration 9324) over source, all/selected set, date, reason and every attestation; a different payload is `REISSUE_KEY_REUSED`; a legacy draft with a NULL fingerprint is refused, never guessed.
- **Atomic transitions.** Approve/cancel take a per-run lock and move the header with a conditional `status='DRAFT'` update plus a matching line update in one transaction; a losing concurrent action gets `REISSUE_CONFLICT`/`REISSUE_STATE`. One active draft per obligation is preserved.
- **Beneficiary name.** The frozen beneficiary is the selected employee bank record's beneficiary name for the intended date, not the employee master; original frozen net amounts are unchanged.
- **No accounting.** Reissue posts/reverses nothing and never recalculates; original files are never mutated. Audit logs carry actor, action, reference, count and total — never account numbers or amounts. All capabilities granted to no role.
