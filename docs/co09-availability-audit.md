# CO09 — Production Order Component Availability Check: audit and implementation-ready specification

**Status: audit of a delivered slice.** §1–§8 are the audit as written at `a39fa0b` + the Part A/B follow-up, when nothing was implemented; §9 records what slice 1 has since delivered, and what the review of that slice corrected. It changes no schema and claims no parity.

## 1. What CO09 is, in SAP's own words

### Not established — do not implement these as fact

- **The literal initial-screen field list of CO09** (material, plant, and checking rule are attested by [third] and course material; whether storage location, batch, MRP area, and "Display scope of check" are selection fields or only display sections is *not* confirmed by the [help] text I read).
- **The standard PP checking-rule keys** (rule `A` for sales is attested by [third]; the production-order rules and their scopes are not evidenced here). The repository already refuses to invent them: a checking rule must already stand, and *"blank is not a default rule and is not PP"* (`src/modules/production/checking-control.ts`).
- **Whether an availability check writes a *release* decision** (the community sources describe `Release material: no release if missing parts` in OPJK; this repository deliberately does not store release control, so parity on that point is unavailable, not merely unimplemented).
- **Any claim of exact CO09 parity.** What can be built here is *an ATP-style component check with commitment semantics, driven by the configuration this ERP already maintains* — say exactly that, never "CO09 parity".

### What both config modules refuse today, verbatim

`AVAILABILITY_CHECK_GAPS` (`availability-check.ts:29-40`) and `CHECKING_CONTROL_GAPS` (`checking-control.ts:30-39`) state, among others:

- *"No transaction is bound to a checking rule. Order creation, conversion, MRP, and the stock/requirements list do not read this configuration. Saving a scope does not calculate an ATP quantity."*
- *"CO09 stays blocked."* / *"CO09 remains blocked. ATP is not calculated."*
- Nothing anywhere stores a confirmed/committed quantity on a requirement or a reservation. The closest the configuration comes is refusing it by name: *"Planned-order scope B is not stored. A planned order has no confirmed quantity."* and *"Purchase-order scope A is not stored. A stock-transport confirmed quantity is not stored."* (`availability-check.ts:163,185`)
- *"Unrestricted-use stock has no inclusion switch in this scope."*
- *"Storage-location inspection is not stored. Planned orders and dependent requirements have no storage location."*
- Refused inputs by name: `totalSalesRequirements`, `totalDeliveryRequirements`, `replenishmentLeadTime`, `checkWithoutReplenishmentLeadTime`, `materialBlock`, `advancedAtp`, `stockInTransfer`, `dependentReservations`, `storageLocationInspection`, `stockTransportReleases`, `subcontracting`, `independentRequirements`, `specialStock`, `atpQuantity`.

These refusals are the specification's boundary: an implementation may keep them, or the owner may lift a named one — but silence is not permission.

## 4. What a faithful first slice looks like (recommended scope)

Staged exactly as the repository's standing order (UI → DB/schema → backend → support), each stage verifiable alone:

1. **Read-only, no persisted commitment (slice 1).** `/production/order-availability`, capability `PROD.ORDER.AVAILABILITY.CHECK`, alias `CO09` in the term registry as `TIER_1_BUILT` with a *refusal list*, not a parity claim. Input: one production order (+ optional component selection). For each checked component: resolve `material_plant.checking_group`; resolve the rule from `production_checking_control` for (plant, order type, the function matching the order's status — 1 created, 2 released) — **refuse when the row is absent or `no_check` is `X`** — *'A missing record is not configured. It is not a check and it is not a no-check.'*; resolve the scope from (`group`, `rule`) — refuse when the group is null or no scope row stands. Then, over the elements the scope includes, in date order from the requirement date: stock by type, receipts, requirements, **and quantities already committed by earlier checks if any exist** (initially none), and report `required`, `available on date`, `cumulated`, `earliest full coverage date`, `shortage`. Persist nothing.
2. **Commitment, in its own table, append-only (slice 2).** Not columns on `mrp_dependent_requirement` — the repository's rule for confirmations and documents is *a record per posting, read back as the truth*. A `requirement_commitment` table (client, material, plant, requirement reference, checked-at, quantity, supply date, checking rule, scope key, request key, status) with the same replay/fingerprint discipline as `confirmation-movements.ts` gives items 7, 10, 11 and *Reset* a home, keeps the demand snapshot untouched, and lets a check be idempotent per request key. `Check` (preview) writes nothing; `Check and commit` writes one commitment per component; `Reset` reverses by a new record, never a delete (append-only trigger pattern already in use).
3. **Status, only after slice 2.** Widening `production_order_status_ck` for `MATERIAL_SHORTAGE` (and a committed marker) is a separate stage with its own migration; the SAP behaviour (status set by the check, cleared by a later check that finds everything) is only honest once commitments exist. Release blocking stays **out**: `no_check`/release control is not stored here and the refusal is on record.
4. **Deliberately not in this feature:** advanced ATP, product allocation, PP/DS, transport/scheduling integration, sales and delivery requirements, special stock, subcontracting, stock in transfer, independent requirements, batch-level ATP, storage-location-level sections, replenishment lead time as a fallback date source. Each is refused *by name* on the screen, in the same style as CO11N's refusal list.

## 5. Open decisions for the owner (do not guess these)

1. **Authoritative requirement date** when the snapshot date was not copied from a dependent requirement (order start vs operation start). Which is honest, and what does the screen say when they differ?
2. **BOM re-read:** may the check consult `material_bom_item` flags (phantom/bulk/item category) *today*, or must it use only what the order snapshotted? Snapshot-only is consistent with CO11N's "a later routing edit is not read" rule — but then the exclusion of phantoms/bulk may be unrepresentable for orders created before the flags existed.
3. **Missing `checking_group` / missing scope row:** refuse per component (recommended, matches both config modules' wording) or skip the component silently (never).
4. **Rule resolution when the order type's control names no rule:** `production_checking_control.checking_rule` is optional. Without a rule there is no scope. Refuse with the remedy "maintain the checking rule on the checking control record" — confirm, because it makes most tenants unable to run the check until configured.
5. **Does the check post anything to the order** in slice 1 (recommended: no, not even a timestamp — SAP's own "the missing parts list is not stored when you exit" supports a pure display), and if not, is the term registry `coverage_tier` still `TIER_1_BUILT` with a documented gap list?
6. **Commitment identity:** is the request key per (order, component, check run) or per component alone? The CO11N precedent says one key per document written; a re-check must not double-commit.
7. **Closed periods and stored commitment dates:** does a supply date in a closed period affect the check, or is that purely a posting-time concern (recommended: posting-time only, stated on screen)?
8. **Collective check** in COOIS: in scope for the first release or deferred with the missing-parts list? SAP's worklist-order semantics (§1 item 11) make this a real behaviour, not a nicety.
9. **`check_on_save`** in the order screens: wire it (CO01/CO02 would read the control and run a check, which the config comment currently forbids: *"Saving this record does not run an availability check, create an order, or release one."*) or leave it refused until slice 2 exists.

**Three readings this slice settled, all in the module's header:**

- **The scope's switches are honoured as the configuration defines them, and only as far as the ledger can carry them.** `plannedOrders` `A` (firmed only) and `X`, `productionOrders` `X`/`F`, `receiptsInPast` `B`, `purchaseRequisitions`, `purchaseOrders`, `reservations`, `dependentRequirements` (which also governs dated component demand, the same element the list treats as one demand stream) and `includeSafetyStock` each select elements and move the figures. The stock-type switches are read with the meanings `availability-check.ts` gives them, not with the meanings their names suggest: `includeRestrictedUse` is *"Include restricted-use batches"* — the label on the form and in the validator — and unrestricted-use stock has no inclusion switch in this scope. So **a blank `includeRestrictedUse` is supported** using the ledger's existing stock-type behaviour, which draws unrestricted-use and quality-inspection stock as one opening element and no other type (`MRP_AVAILABLE_STOCK_TYPES`, `stock-requirements.ts:42`), while **`includeRestrictedUse = 'X'` is refused** because restricted-use batch elements are not something this ledger has; `includeQualityStock = ' '` and `includeBlockedStock = 'X'` are refused on the same ground. A refusal publishes no quantity, and no claim is made that the list can distinguish stock types it cannot represent.
- **Own-demand exclusion identifies the exact line being checked.** The balance is taken to the component's requirement date with one row left out — this order's *and this item's* dated component demand, matched on the row's own `documentNumber` plus `documentItem`, which is the component's item number (`stock-requirements.ts:496`) — because the demand being checked cannot cover itself. Every other requirement on the ledger stays in the demand, including a **sibling line of the same order and the same material**: two lines of 10 against 12 of supply are each answered short by 8, not covered at 10 each. Excluding the order as a whole was the defect the review found; the regression test pins both directions, sibling counted and own line subtracted exactly once.
- **A component in another plant is refused, and is not supported by this slice.** The configuration is read at the component's own plant while the list, the message and the drill-down are at the order's plant, and `production-orders.ts:521` lets a caller set a component's plant independently of the order's. So a component whose plant differs from the order's is refused before any list is called, with a message naming both plants; neither plant is substituted for the other, and no cross-plant ATP is attempted.

**What still stands, unchanged from the delivery:** `committedQuantity` is `null` on every line, always, because no commitment record exists; a run writes nothing, so two runs of one order agree and neither reduces what the next order can take — that is the whole stability promise a read-only slice can make, and it is not a snapshot, a reservation, or a lock; requirement dates and quantities stay the order's own snapshot; and no CO09 parity is claimed on the screen, in the module, or here.

**Fixed in the second pass of the same review (2026-10-25, minimal correctness triage), ranked by the wrongness each could publish. F7 was the exception there: it was *disclosed*, not corrected, and the fourth pass below is what closes it.**

- **F4 — a technically complete order was answered with figures.** Completion moves the order out from under the ledger in three places at once, and not all of them together: the list takes an order receipt only from a created or released order (`stock-requirements.ts`, `o.status in ('CREATED','RELEASED')`, carrying the comment *"TECHNICALLY_COMPLETED is not an open receipt. Do not add it here."*), it reads dated component demand from the same status pair, and the open dependent requirements are keyed on their own `status = 'OPEN'`, which completion does not maintain (`production-order-change.ts` changes the header, the completion pair and a change document, and no dependent requirement). So a completed order loses its supply and half of its demand, and the release-time checking control — business function 2, which is what a completion resolves to — was then consulted and answered normally. The order is now refused at its own state, before any configuration is read and before any element is counted: every line is `UNSUPPORTED` with a message naming the completion, saying which parts of the ledger no longer hold it and pointing at its revocation; no element list and no figure is rendered, and the header carries the same refusal. What was removed is the warning that used to sit *beside* an answered figure. The half of the same rule that affects *other* orders — a finished order no longer competes for the same supply — is the ledger's own behaviour and is deliberately left alone; this fix only stops the completed order from being read as an open one.
- **F5 — a horizon that stops before the requirement date published a balance it could not support.** `horizonEnd` bounds the search; the requirement date is the date the answer is claimed for, and the list refuses a horizon only when it lies in the past. A horizon of 2026-06-05 on a line due 2026-06-10 was answered `AVAILABLE` with a cumulated figure assembled from rows ending five days before the date printed beside it. A line whose horizon is not in the past but ends before its own requirement date is now refused per line, before the list is called, and the refusal keeps the requirement date it could not reach. A horizon that reaches the date still answers however tight it is, and no caller-set horizon is widened or narrowed here.
- **F7 — counted elements arrive without a unit, and were summed as if they had one.** The list selects quantities and leaves the unit behind: `purchase_requisition_item`, `purchase_order_item`, `planned_order` and `mrp_dependent_requirement` each store a `unit`, and no availability query reads it, so the rows this check cumulates cannot be compared with the base unit at all. The unit rule the check could enforce it already enforced — a *component line* whose unit is not the material's base unit is refused outright. Answered lines now carry one warning naming which counted kinds enter the figure in their own document's unit and stating that nothing was converted, so the number is read as the arithmetic of the rows shown rather than as a base-unit coverage statement. No conversion factor is invented and no figure is adjusted: unit-aware cumulation is a change to the ledger's rows, not to this screen, and it is recorded here rather than taken. **So at that pass the mixed-unit limitation stood as a correctness defect in the figures themselves, and only its visibility had changed.** — an answered cumulated figure can still add a requisition in its order unit to stock in the base unit — and only its visibility changed. Anyone comparing this screen's shortage against a purchasing document's quantity had to re-read the units, because the check could not and no claim was made that the arithmetic was unit-safe. That is the sentence the fourth pass below makes historical.
- **F8 — a check that answered nothing called itself a partial check.** `status` keyed off the order's no-check indicator alone, so a run with `checkedCount 0` and every line refused reported `PARTIALLY_CHECKED`. It reports `NOT_CHECKED` whenever no line was answered, and the result now carries `configurationGap` — true only where the refusal is a record that does not stand (no order type, no checking control, a control naming no rule). `OrderAvailabilityWorkbench.tsx` buckets its banner on that flag rather than on the status, which keeps the two distinguishable now that the status is honest: a missing control is still `incomplete-config`, a standing no-check and a completed order are `not-checked`, and a wholly refused component list states in the warnings that `NOT_CHECKED` is the absence of an answer and not a shortage.

- **F10 — a shortfall larger than the line it was computed for (third pass, 2026-10-26: interpretation corrected, arithmetic left alone).** The formula is `shortage = max(0, required − cumulatedOnDate)`, where `cumulatedOnDate` is the balance of the *whole counted scope* at the requirement date with only this line's own demand row removed. When the demand dated before the line already exceeds the supply the scope counts, that balance is negative and the shortfall grows past the requirement: the fixture answers a 10.000 requirement with 2.000 of stock against 3.000 of reservation and 6.000 of open dependent requirement as **short by 17.000**, with `coveredQuantity` 0.000 — so cover and shortfall are not complements of the requirement in that case. That is the cumulated ATP reading, and it is the right one: the quantity that must still arrive at the date for this line to be covered is its own requirement *plus* the hole in front of it, and clamping the figure to 10.000 would hide supply this order genuinely needs. The defect was that nothing said so. The SHORT sentence now names the composition whenever it exceeds the line (the requirement of the line, the remaining deficit, and that the figure is not this line's unmet quantity), the result contract documents all three figures, and the two table columns read *Covered of requirement* and *Shortage against balance* instead of *Covered* and *Shortage*, which was where a 17.000 beside a 10.000 could be read as a claim about the line alone. The clause is tied to the case: a shortage that does not exceed the requirement keeps the terse sentence, and every existing figure is unchanged.

**F7, corrected in the fourth pass (2026-10-26) — the figures themselves, not their disclosure.** The units were traced to their columns rather than reasoned about: `purchase_requisition_item.quantity`/`.unit`, `purchase_order_item.quantity`/`.unit`, `planned_order.quantity`/`.unit`, `mrp_dependent_requirement.quantity`/`.unit`, `reservation_item.required_quantity`/`.unit_of_measure`, `production_order.order_quantity`/`.unit_of_measure` and `production_order_component.required_quantity`/`.unit_of_measure` each store a unit beside the figure the list reads, every one of them `notNull`, and `stock_quantity` and `material_plant.safety_stock` store no unit at all.
