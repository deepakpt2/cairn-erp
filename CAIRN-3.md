## §0.3 Document-set size and rotation rule `AGREED · v1.70`

**Owner instruction, 2026-10-13 (recorded as R-24 / D-093).**

| Rule | Detail |
|---|---|
| **Hard ceiling** | No part of the canonical log may ever exceed **400 KB (400,000 bytes)**. The 400 KB figure is read conservatively (decimal KB, the smaller interpretation), so either reading of "400kb" is satisfied. |
| **Rotation trigger** | A live part **rotates as soon as it passes 360 KB (360,000 bytes)** — i.e. once it is "becoming closer" to the ceiling, the next numbered file is started rather than waiting for the limit. |
| **New part** | The next part is created as `CAIRN-<n>.md`, continues section numbering and the change-log version sequence without a gap, and is declared the live part. |
| **Continuation notice** | The last part announces that the set continues in the new part; the new part names every earlier part it continues. Both directions are mandatory. |
| **Frozen parts** | A rotated part is frozen: further edits are limited to pointer/continuation lines and corrections that cannot be deferred (each such edit must keep the part under the ceiling). New substantive content is appended only in the live part. |
| **Measurement** | Byte size on disk (`stat -c %s`), checked in the same turn any canonical file is edited. |

### 26.256 B-240 — The Docker stack surveyed against multiple tenant databases: what changes, and the one privilege decision both storage models share `SURVEY RECORDED · STORAGE MODEL STILL OPEN`

The owner asked how the current Docker setup, which carries the database name in the environment, would work with more than one database. The stack was read rather than described generically.

**How it works today.** The name appears in three places. `POSTGRES_DB: cairn` creates the first database when the volume initialises. Two literal connection strings in `docker-compose.yml` embed the name: the `app` service gets `postgresql://cairn_app:…@cairn-postgres:5432/cairn`, and the one-shot `migrate` service gets that plus the owner-role URL for the same database. In code, `connectionString()` reads `DATABASE_URL` once and caches a single pool — `max: 10`, `idle_timeout: 20`, and `prepare: false` because PgBouncer in transaction mode is the intended production pooling (D-026).

**The separation is deliberate and documented in the image itself.** `docker/postgres/10-app-role.sh` creates the runtime role as `CREATE ROLE cairn_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS` and grants it `CONNECT ON DATABASE cairn` — one database, named. The Dockerfile's `operations` target is commented "One-shot administrative tools; direct DB access; never the web runtime role", and `assertApplicationRole()` fails closed if the runtime URL points at the migration role. So the web container today **cannot** create a database, cannot create a role, and cannot connect to any database but `cairn`.

**What multiple databases changes here.** No new containers: one `postgres:17-alpine` service hosts any number of databases, and `POSTGRES_DB` only makes the first. Six things do change. (1) Privilege — either the app is given the owner URL, which undoes the separation above, or a narrow `cairn_provision` role is created with `CREATEDB` and no table access, or provisioning leaves the app entirely and becomes a separate service, which makes tenant creation asynchronous. Every new database also needs `GRANT CONNECT ON DATABASE` to `cairn_app`. (2) The connection string becomes a template — `DATABASE_URL_TEMPLATE` with the client substituted, or discrete host/port/user/password variables — and because a database name cannot be a bind parameter the key must be validated before interpolation; the repository already has that guard shape in `sqlSafeSetting` (`^[A-Za-z0-9]{2,4}$`). (3) The module-level singleton pool becomes a cache of pools, each needing a smaller `max`, idle eviction and a cap, or PostgreSQL's default `max_connections` of 100 is exhausted at roughly thirty tenants. (4) Migrations become a fleet job: `migrate` runs once today and `app` waits on `service_completed_successfully`, so a tenant created after that container exited must be migrated by whatever provisions it, and every release must loop a registry. (5) The single `postgres_data` volume still holds every tenant database, so a snapshot remains a fleet backup and per-database `pg_dump` becomes possible, but point-in-time recovery stays per-cluster — isolating that means a cluster per tenant, and then compose grows per customer. (6) `cairn_internal` is `internal: true`, so the app has no egress: a hosted or pooled external cluster is unreachable from this stack as written.

**One note on the token.** `CAIRN_PROVISIONING_TOKEN` already gates *who* may provision — it is what renders the owner-token field on the tenant form — but a token decides authorisation, not which database role connects. It does not answer the privilege question.

**The same question under schema-per-tenant is much smaller.** One database, one URL, one pool of ten, no template, no pool cache and no `max_connections` pressure; `migrate` loops schemas inside the same database, and `SET search_path` replaces `SET LOCAL cairn.client` in the same single funnel. Creating a schema still needs a privilege the runtime role does not have, so item (1) is the one decision **both** models share — and it is a decision about where provisioning privilege lives, not about tables.

**Cost measured while answering.** Applying every migration to an empty database produced 86 tables and 73 row-level-security policies in **912 ms**, on a throwaway database that was dropped afterwards. Provisioning is cheap in wall-clock terms; the cost is in the fleet, the pools and the tests, not in the creation.

**Open.** The storage model, and with it where provisioning privilege lives. Settled in the meantime: name and key asked separately, no start option (R-68).
