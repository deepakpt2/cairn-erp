## §26.980 — ME49 contracted: one event is compared, and it does not buy

**B-968.** SCR-159. The owner's package (2026-10-22, three parts) is the contract. ME49 compares the quotations that already stand for one event. It is not a revision, not a condition, not an exchange rate, not a report run, not an award, and not an order. ME47 and ME48 still refuse a status, a revision stack, a condition, a currency column, and an award. This round does not weaken that refusal. A supplier portal, EDI, email dispatch, a rejection, and an award stay later. Balance-form suggestions stay deferred.

**What already stands, and this round does not rebuild.** One quotation prices one request. The event number groups the requests. A collective number is a label. The supplier is on the request. The currency is the company's, on the event. The net price and the price unit are on the quotation item. The price per one unit is calculated. Migrations `9096` and `9097` are not edited. There is no schema stage. There is no `9098`.

**The comparison.** The event number is the key. A collective number that matches one event resolves that event and is named as a label. A collective number that matches more than one is refused and names the event numbers. Events are not merged. The purchasing organisation is required, must stand, and must be the event's. There is no purchasing-organisation authorization object. A plant and a material are optional filters. An unknown plant or material is refused. Another tenant's event is the same miss.

**The price.** The currency is the event's company currency. A posted currency is refused and names that currency. An exchange rate is not read. The compared price is the net price per one unit of the unit that was asked. It is calculated. It is not stored. Rank is within one event item, lowest first, and equal prices are ordered by supplier number for display only. Equal prices share a rank. They are not called commercially superior. The next distinct price takes the competition rank. A zero price is an offer and ranks when it can be compared. A missing offer is not a zero and is not ranked. A quantity mismatch is shown and is not a disqualification. Rank is by the comparable unit price, not by the extended cost. The extended cost for the quantity that was asked is shown and is not stored.

**The unit.** The comparable unit is the event item's unit. The comparison is grouped by the event item, not by the material number alone. The same unit compares directly. A standing material unit conversion converts by integer arithmetic, half up at scale 4. Alternative quantity times numerator, divided by denominator, equals base quantity. When the offered unit is the alternative and the asked unit is the base, the price per asked unit is the price per offered unit times denominator, divided by numerator. The reverse uses the inverse ratio. No conversion path means the offer is not comparable and is not ranked. The float path in `unit-conversion.ts` is not used.

**The date.** A day after the deadline does not hide a standing quotation. The evaluation date is the server's date. It is shown. It is not an input. A posted date is refused.

**Refused by name, so a later round does not mistake refusal for absence:** a stored status, a revision, a condition, a discount, freight, a tax, a landed cost, a currency column, an exchange rate, a report-run record, a stored rank, a stored normalized price, an award, a purchase order, a request key, an outbox, a uuid, a goods movement, and a journal. Viewing writes nothing, including a change document.

## §27.010 — The grant policy for future tables: a migration says what it needs

**B-998.** No screen, no tcode, no business semantics. This closes the audit opened after `9186` and `9187`: the default was fixed, but nothing yet stopped the next table from being written as if the old `arwd` default still stood. The safeguard is a convention plus a check, not a redesign of the roles.

**What stands, unchanged.** The effective default for a table created by `cairn` in `public` is `{cairn_app=ar/cairn}`: `SELECT` and `INSERT`, no `UPDATE`, no `DELETE`, no `TRUNCATE`, and no default at all for sequences, functions or types. `cairn_app` remains non-owner, `NOSUPERUSER`, `NOBYPASSRLS`, `NOINHERIT`, with `USAGE` but not `CREATE` on the schema and no role membership. `9183` through `9187` were not edited; the 13 restricted append-only tables, including the two `9185` production-order operation snapshots, keep their `ar` ACL and the owner keeps `arwdDxtm`. **The convention, written down.** `docs/migration-authoring.md` is the authoring guide — an operational document beside `docs/production-tcode-order.md`, not a parallel design document; the decision itself is D-145 above. Append-only and snapshot tables state the revoke. A mutable table grants only what a verified service does. A sequence is granted on its own. Administrative objects get nothing. Tenant deletion is untouched, because the `client` cascade runs on the owner side (D-041) and still removes rows in a table whose own `DELETE` is revoked.

**The check.** `tests/migration-grant-policy.test.ts`, eight tests against the live catalog. Two of them derive their expectation instead of listing it: the protected set is every table any migration revokes from `cairn_app`, and the required-mutable set is every table the application updates or deletes, resolved from the services through the Drizzle schema root. A migration newer than the ledger's `9186` timestamp must declare its tables, must not use `serial` without a sequence grant, and must not widen the default. Failure messages name the file, the table, the privilege, and the statement to add.

**The proof, both ways.** Green: 8/8 with the restricted default, the append-only denials, the 151 tables needing `UPDATE` and 74 needing `DELETE` all satisfied, and the probe showing an identity table insertable but not updatable by the runtime role while a serial table is unwritable until `grant usage` — probes dropped and their absence asserted. ## §27.014 — A confirmation moves the stock the material asks for

**B-1002.** CO11N posts goods movements, and it posts them inside its own transaction. One migration, two columns, no new table, no new ledger, and no counter anywhere.

**What was there before.** The time ticket wrote a confirmation and stopped. `MOVEMENT_NOTE` said that backflush was not configured and that no goods movement was proposed, and the capability description said the same thing to anyone who read the registry. Both sentences were true, because no field in the database carried the mark they described. A component was withdrawn on MIGO by hand, and the finished good was received on MIGO by hand, and nothing linked either document to the confirmation that proved the work was done. CO13 refused a cancellation by saying it touched no movement, which was true for the same reason.

**What stands now.** `material_plant` carries `backflush` and `automatic_goods_receipt`, both `boolean not null default false`, migrated in `9188_confirmation_goods_movement.sql` and maintained on the material's MRP view — the same view that already held the underdelivery tolerance a confirmation reads. Migration `9188` also corrects the four sentences in `capability` and `term_registry` that said no movement was posted. A component whose material is marked is withdrawn against the order for the share its confirmation's yield represents: the requirement on the order's own component snapshot, converted to base units, less the issues that still stand, read with the same `lineNotReversed` and `OPEN_PRODUCTION_DOCUMENT` rule MIGO applies. The proposal is truncated, capped by what remains open, and never the whole requirement — a partial confirmation of four units from a ten-unit order against a twenty-unit requirement owes eight, whatever else it has already been issued. A final confirmation of a marked finished good receives its own yield through the receipt service; a partial never receives, and the receipt service's own over-receipt refusal is the ceiling. Both postings run through the goods-movement services the MIGO matrix uses, which gained the `options.tx` shape `createProductionOrder` already follows — `postGoodsIssue(input, 'MIGO', { tx })` — so a refusal from either service rolls the confirmation back with it, and no confirmation can stand beside a movement it was owed. Each document carries its own request key, derived from the confirmation's (`<KEY>-BF` and `<KEY>-GR`, folded and never truncated when the key is already at sixty-four characters), because one material document is unique per client and request key. CO13 now refuses a cancellation while a document the confirmation caused still stands, naming that document and pointing at the goods-movement screen; after a reversal the cancellation is allowed, the confirmation stays as posted, and the requirement is open again on the same read.

**Refused by name, because canon does not carry it.** Scrap is not grossed into a component quantity: the order's component snapshot stores no scrap indicator, so the only honest figure is the snapshot's own. No order type and no scheduling profile switches a receipt on or off: `production_order_type` stores an order category and a description, and the conversion-priority note in the SAP support portal describes customising this application does not have. No batch is determined for a batch-managed component, no storage location is invented for a receipt beyond the plant default the receipt service already applies, no reservation is cleared by an issue, and no "final issue" sweeps what a partial sequence leaves open. Automatic reversal is not attempted from CO13: the reversal service opens its own transaction and exposes no path inside a caller's, and what SAP's CO13 does with a backflush movement is not evidenced in this repository's canon, so the cancellation is refused instead of approximated.

Movement, MIGO, receipt, reversal, document-display, CO13 and CO15 suites: 26 of 26 and 27 of 27 and 33 of 33 in their batches. `tsc --noEmit` is at the same 161 errors it was at before this work, `lint:ip` at the same 138 occurrences, and `npm run db:verify` at 13 of 13. `tests/material-period-control.test.ts` fails 3 for an unrelated reason that reproduces on a clean tree at this commit.
